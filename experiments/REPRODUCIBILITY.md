# Experimentation and Reproducibility Guide

This document describes the execution procedures, configuration semantics, result schemas, data-integrity rules, and sources of measurement uncertainty for benchmarking load-balancing algorithms in `self-balancing-router`.

---

## 1. Executing and Repeating Benchmarks

The benchmark suite is driven by the Python experiment orchestrator located in `scripts/run_experiment.py` (implementing `experiments/orchestrator/`). The orchestrator executes scenario-driven HTTP workloads generated by Grafana k6 against an isolated multi-container Docker Compose deployment of the Go reverse proxy and five simulated backend services.

### Basic Execution Command

```powershell
python -B scripts/run_experiment.py `
  --scenario scenario_1_homogeneous `
  --policy round-robin `
  --repetitions 3 `
  --seed 42 `
  --proxy-port 18080 `
  --compose-project sbr-eval `
  --vus-preallocated 20 `
  --vus-max 50
```

### Command-Line Arguments

| Flag | Default | Description |
|---|---|---|
| `--scenario` | `scenario_1_homogeneous` | Scenario ID, catalog index (1–7), or direct file path to scenario JSON. |
| `--catalog` | `experiments/scenarios.json` | Path to master scenario catalog. |
| `--policy` | `round-robin` | Pluggable proxy routing policy (e.g. `first-eligible`, `round-robin`, `least-requests`, `p2c`, `p2c-peak-ewma`, or MAB policies). |
| `--repetitions` | `1` | Number of independent, sequential experimental trials to execute. |
| `--seed` | `42` | Base integer seed for deterministic pseudorandom number generator progression. |
| `--output-dir` | `experiments/results` | Root output directory where isolated trial directories are written. |
| `--compose-project`| `sbr-experiment` | Dedicated Docker Compose project name ensuring complete container isolation. |
| `--proxy-port` | `8080` | Host port on which the reverse proxy will listen. |
| `--admin-ports` | `19091,19092,19093,19094,19095` | Comma-separated admin ports for `backend-a` through `backend-e`. |
| `--k6-exec` | `auto` | Execution mode for Grafana k6 (`auto`, `local`, or `docker`). |
| `--vus-preallocated`| `0` | Explicit override for preallocated virtual users (0 uses scenario recommendation). |
| `--vus-max` | `0` | Explicit override for maximum virtual users (0 uses scenario recommendation). |
| `--dry-run` | `False` | Validates configuration, schemas, and generates artifact skeletons without starting containers. |

### Development Stack Isolation

To avoid interfering with the local development stack (running on port `8080` with backend admin ports `8081`–`8085`):
1. Always specify an alternate proxy port (e.g. `--proxy-port 18080`).
2. The orchestrator automatically defaults backend admin ports to `19091`–`19095`.
3. The orchestrator enforces pre-flight TCP port collision checks (`verify_no_port_conflicts`) and will refuse to start if any specified port is bound.
4. Each trial cleans up its own containers using `docker compose -p <project> down -v --remove-orphans`, ensuring no lingering containers or networks remain.

## 2. Seed and Configuration Semantics

### Deterministic Seed Progression

Experiments evaluate both stationary and non-stationary conditions using uniform random jitter on backend processing delays. To ensure independent, non-overlapping random sequences across repeated trials:

1. **Trial Seed Derivation:**
   For trial index $i \in \{1, 2, \dots, N\}$ with base seed $S$:
   $$\text{seed}_{\text{trial}} = S + i - 1$$
2. **Backend Seed Derivation:**
   Each backend instance (`backend-a` through `backend-e`) receives a distinct, non-overlapping deterministic seed:
   $$\text{seed}_{\text{backend-}k} = \text{seed}_{\text{trial}} + k \quad \text{where } k \in \{1, 2, 3, 4, 5\}$$
   These seeds are injected into the backend containers via `SBR_BACKEND_<ID>_DELAY_SEED`.
3. **PRNG Independence:**
   Each backend process runs its own seeded `math/rand/v2` PCG generator. Two trials run with the same seed will produce identical processing jitter samples for identical request arrivals.

### Supported Routing Policies and Parameter Settings

The orchestrator recognizes all eight routing policies implemented in the Go reverse proxy:

1. **`first-eligible`**: Static benchmark selecting the first available healthy backend.
2. **`round-robin`**: Deterministic circular rotation across healthy backends.
3. **`least-requests`**: Dynamic concurrency-aware routing targeting the backend with the fewest active in-flight requests.
4. **`p2c`**: Power of Two Choices picking two random candidate backends and selecting the one with fewer in-flight requests.
   - `--p2c-seed <int>`: PRNG seed for candidate sampling (`SBR_PROXY_P2C_SEED`, default: `1`).
5. **`p2c-peak-ewma`**: Power of Two Choices picking two candidates and choosing the lower Peak EWMA latency $\times$ in-flight score.
   - `--p2c-seed <int>`: PRNG seed for candidate sampling (`SBR_PROXY_P2C_SEED`, default: `1`).
   - `--peak-ewma-decay <duration>`: Aging window for Peak EWMA latency estimates (`SBR_PROXY_PEAK_EWMA_DECAY`, default: `10s`).
   - `--peak-ewma-initial-rtt <duration>`: Cold-start penalty RTT for unobserved backends (`SBR_PROXY_PEAK_EWMA_INITIAL_RTT`, default: `10ms`).
6. **`ucb1`**: Stationary Multi-Armed Bandit using upper confidence bound exploration based on observed latencies:
   - `--mab-latency-scale <duration>`: Scale duration for linear reward normalization $r_t = 1 - \frac{\text{duration}}{\text{scale}}$ clamped to $[0, 1]$ (`SBR_PROXY_MAB_LATENCY_SCALE`, default: `100ms`).
7. **`sliding-window-ucb`**: Non-stationary MAB restricting sample statistics to a fixed-size FIFO observation window:
   - `--mab-latency-scale <duration>`: Scale duration for linear reward normalization (`SBR_PROXY_MAB_LATENCY_SCALE`, default: `100ms`).
   - `--mab-sw-window <int>`: Number of recent observations retained per arm (`SBR_PROXY_MAB_SW_WINDOW`, default: `1000`).
8. **`discounted-ucb`**: Non-stationary MAB using geometric discounting of past observations:
   - `--mab-latency-scale <duration>`: Scale duration for linear reward normalization (`SBR_PROXY_MAB_LATENCY_SCALE`, default: `100ms`).
   - `--mab-discount-factor <float>`: Discount factor $\gamma$ strictly between 0 and 1 (`SBR_PROXY_MAB_DISCOUNT_FACTOR`, default: `0.99`).

### Policy Equivalence and Fairness

To guarantee that comparisons between routing policies are scientifically valid:
- **Identical Scenario Definitions:** All policies consume the exact same arrival-rate stages, timeline boundaries, and degradation/recovery events.
- **Identical Upstream Transport:** All policies run within the same Go proxy infrastructure, using identical HTTP connection pool limits, timeouts, and health check intervals.
- **Identical Backend Capacities:** Backend worker pool sizes (4 workers) and FIFO queue capacities (32 requests) are identical across all policy evaluations.
- **Trial Isolation:** Containers are completely stopped and recreated between trials, resetting all in-memory routing policy state (e.g. EWMA latency estimates, active connection counters, bandit arm weights) and backend queues.

## 3. Result Schemas and Metric Definitions

Every trial creates an isolated directory:
`experiments/results/<scenario-id>/<policy>/run-XXX/`

The directory contains 9 standardized artifacts:
1. `metadata.json` — Environment, tool versions, seeds, git SHA, timing parameters, and policy configuration.
2. `scenario.json` — Full scenario specification used for the trial.
3. `compose.override.yaml` — Exact Docker Compose environment overrides injected into containers.
4. `events.json` — Administrative events planned vs actual execution records.
5. `k6-summary.json` — Native k6 execution summary report.
6. `k6-output.log` — Raw stdout and stderr from k6 workload generator.
7. `requests.csv` — Timestamped request-level observations.
8. `metrics.json` — Derived trial-level summary statistics.
9. `raw-metrics.json.gz` — Compressed raw diagnostic metrics export from k6.

### `requests.csv` Column Specification

`requests.csv` contains 17 columns:

| Index | Column | Type | Description |
|---|---|---|---|
| 0 | `request_index` | Integer | Monotonic zero-based request observation index. |
| 1 | `timestamp_iso` | String | ISO 8601 UTC timestamp of request completion from k6 metric point. |
| 2 | `elapsed_seconds` | Float | Elapsed wall-clock seconds from workload start to request completion. |
| 3 | `duration_ms` | Float | End-to-end HTTP request duration in milliseconds. |
| 4 | `status_code` | Integer | HTTP response status code (0 for transport/network error). |
| 5 | `outcome` | String | Classification: `success`, `overload_503`, `http_error`, or `transport_error`. |
| 6 | `is_success` | Boolean | `True` only for HTTP 200 responses. |
| 7 | `is_overload` | Boolean | `True` for HTTP 503 responses. |
| 8 | `is_transport_error`| Boolean | `True` for connection resets, dial timeouts, or status 0. |
| 9 | `backend_id` | String | Serving backend identifier (`backend-a` through `backend-e`) when directly observable from response body; empty string `""` on errors or when unobservable. |
| 10 | `overload_origin` | String | For HTTP 503: `backend` (queue full), `proxy` (no healthy routes), or `unknown`. Empty string for non-503. |
| 11 | `phase` | String | Workload timeline phase: `warmup`, `measurement`, or `cooldown`. |
| 12 | `interval` | String | Dynamic event timeline interval based on request dispatch time (e.g. `baseline`, `degradation:backend-b`, `recovery:backend-b`, `steady_state`). |
| 13 | `spans_boundary` | Boolean | `True` if request dispatch interval differs from request completion interval. |
| 14 | `scenario_id` | String | Benchmark scenario identifier. |
| 15 | `routing_policy` | String | Proxy routing policy evaluated during the trial. |
| 16 | `trial_index` | Integer | 1-based sequential trial repetition number. |

### HTTP 503 Overload Origin Classification

HTTP 503 responses can originate from two distinct architectural boundaries:
- **Backend Overload (`backend`):** The backend worker pool was busy and its FIFO queue reached capacity. The backend returned HTTP 503 with JSON payload `{"error":"backend overloaded"}`.
- **Proxy Routing Unavailable (`proxy`):** The reverse proxy was unable to route the request (e.g., all backends unready or policy selected no candidate). The proxy returned HTTP 503 with plain text `request routing is unavailable\n`.
- **Unknown (`unknown`):** An HTTP 503 was received without definitive body evidence (e.g. empty response or intermediary gateway error).

Both `requests.csv` (`overload_origin`) and `metrics.json` (`outcomes.overload_503_breakdown`) report this breakdown.

### Latency Distribution Separation

To maintain scientific validity:
- `latency_ms.successful_requests`: Computes count, mean, min, p50, p90, p95, p99, and max **strictly on successful HTTP 200 responses**.
- `latency_ms.all_requests`: Computes latency over all responses, including fast error rejections.
- Fast rejections (e.g. immediate 503 queue overflows or connection resets) execute in $<2\text{ms}$. Pooling them into the successful latency distribution would artificially depress average latency during periods of severe backend degradation.

## 4. Trial Validity Criteria

The `DataValidator` automatically verifies each completed trial against strict integrity checks. A trial is marked `valid: true` in `metadata.json` only if all criteria pass:

1. **Artifact Completeness:** All 7 required artifact files must exist on disk and be non-empty.
2. **Workload Integrity (Offered Load):** `dropped_iterations == 0` in both `k6-summary.json` and `metrics.json`. Any dropped iterations indicate VU starvation in k6, invalidating the offered open-loop load.
3. **Cross-Artifact Count Equality:** The total request count in `requests.csv`, `metrics.json`, and `k6-summary.json` must match exactly ($N_{\text{CSV}} = N_{\text{metrics}} = N_{\text{summary}}$).
4. **Latency Bounds and Non-Negativity:** All latency metrics must be finite, non-negative ($duration \ge 0.0$), and within plausible execution bounds ($\le 600,000\text{ms}$).
5. **Distribution Consistency:**
   - $\sum \text{status\_distribution} = N_{\text{total}}$
   - $\sum \text{outcome\_distribution} = N_{\text{total}}$
   - $\sum \text{overload\_503\_breakdown} = N_{503}$
   - Latency sample count for successful requests equals $N_{\text{successful}}$.
6. **Administrative Event Verification:** All scheduled events in `events.json` must record `success: true` and `verified: true` with administrative latency $< 5.0\text{s}$.
7. **Failure Preservation:** If any check fails, the trial is marked `valid: false` with explicit failure reasons recorded in `metadata.json`. All trial files are preserved on disk for post-mortem analysis.

## 5. Sources of Nondeterminism and Measurement Uncertainty

### Deterministic Components
- **Workload Schedule:** Open-loop arrival rates, stage durations, and target RPS are constant-arrival schedules generated deterministically by k6.
- **Backend Delays and Jitter:** When seeded via `SBR_BACKEND_<ID>_DELAY_SEED`, delay generation uses deterministic uniform pseudorandom sampling.
- **Administrative Event Schedules:** Trigger offsets are specified relative to workload start.

### Nondeterministic Components
- **Goroutine and OS Thread Scheduling:** Go runtime preemption and OS kernel thread scheduling introduce variance in request processing order and reverse proxy lock acquisition.
- **Network Stack Dynamics:** Loopback TCP socket buffers, TCP handshake latency, and kernel packet switching inside Docker bridge networks (`bridge` driver) introduce non-zero transport jitter ($\pm 0.5\text{ms}$ to $\pm 3\text{ms}$).
- **Timer Resolution:** Windows sub-millisecond timer resolution differs slightly from Linux monotonic timers (`CLOCK_MONOTONIC`).

### Workload-Start Synchronization Uncertainty

The orchestrator synchronizes administrative event schedules with the k6 workload start using an iteration 0 token emitted over stdout or an ephemeral HTTP webhook:
- **Stdout Token Synchronization:** k6 iteration 0 emits `[SBR_WORKLOAD_START] {"timestamp_ms": ...}`. The orchestrator records both the process wall-clock time and monotonic clock. Pipe latency between k6 and the Python reader thread is measured and recorded in `metadata["timing_summary"]["synchronization"]` (typical uncertainty: $\pm 1\text{ms}$ to $\pm 5\text{ms}$).
- **Webhook Synchronization:** k6 makes an HTTP GET request to `host.docker.internal:<ephemeral-port>/start` (typical uncertainty: $\pm 2\text{ms}$).
- **Fallback Launch Time:** If the start token is not received within 20s, the orchestrator falls back to process launch time with uncertainty bounded by the timeout window ($20\text{s}$).

### Request Timestamp Semantics and Boundary Spanning

k6 metrics points record the timestamp at **request completion** ($t_{\text{completion}}$). The orchestrator derives the request dispatch time as:
$$t_{\text{dispatch}} = t_{\text{completion}} - \frac{\text{duration\_ms}}{1000.0}$$

- **Interval Alignment:** Requests are assigned to experimental intervals based on **dispatch time**, reflecting the state of the system when the proxy routing decision was made.
- **Boundary-Spanning Requests:** Requests where $t_{\text{dispatch}} < T_{\text{event}} < t_{\text{completion}}$ span an event boundary (e.g. dispatched during baseline, completed after degradation). These are explicitly tagged with `spans_boundary = True` in `requests.csv` and counted under `timing_semantics.total_boundary_spanning_requests` in `metrics.json`.

## 6. Persistent Experiment History and Research Journal

The experimental infrastructure automatically maintains a permanent, IDE-accessible research catalog under `experiments/results/`.

### Unique Per-Trial Directories
Every experimental trial is assigned a non-colliding sequential directory:
`experiments/results/<scenario-id>/<policy>/run-XXX/`
- Existing trials are never overwritten.
- Cleanups, container teardowns, and repeated runs preserve all previous results.

### Automated Experiment Index (`index.json` & `INDEX.md`)
The orchestrator maintains two index representations in `experiments/results/`:
1. `index.json`: Structured, machine-readable catalog of all trials, listing timestamps, scenario IDs, routing policies, validity status, total requests, success rates, latency statistics, and relative directory paths.
2. `INDEX.md`: A human-readable Markdown table designed for immediate viewing and navigation within VS Code, featuring direct clickable links to each trial directory.

To rebuild or refresh the index across all historical runs discovered on disk:
```powershell
python -B scripts/run_experiment.py --rebuild-index
```

### Research Journal (`JOURNAL.md`)
`experiments/results/JOURNAL.md` maintains a permanent log of hypotheses, configuration changes, empirical observations, and conclusions across evaluation sessions.
- Pass `--hypothesis "..."` to record scientific expectations into trial metadata and the journal.
- Pass `--note "..."` to attach observations or anomaly notes to the journal entry.
- Direct Markdown editing is encouraged for multi-round analysis and post-mortem syntheses.

## 7. Raw Measurement Archiving and Backup Procedures

### Raw Metrics Preservation and Gzip Compression
k6 emits high-resolution diagnostic points (`sbr_request_observation`). To preserve complete raw data without consuming excessive disk space:
- `--raw-metrics gz` (Default): Compresses `raw-metrics.json` into `raw-metrics.json.gz` using standard gzip (typically 90–95% compression ratio). Preserves all raw timestamps, durations, and diagnostic tags for offline reproduction while saving storage.
- `--raw-metrics json`: Retains the full uncompressed `raw-metrics.json` file.
- `--raw-metrics none`: Discards raw points after CSV/metrics derivation (only if storage is strictly constrained).

### Keeping Results Excluded from Git
To keep the Git repository lightweight, `experiments/results/` is excluded via the root `.gitignore`.

### Backing Up and Archiving Research History
To create an independent archive of all experimental data, indexes, and journals:

#### PowerShell (Windows)
```powershell
$timestamp = Get-Date -Format "yyyyMMdd-HHmmss"
Compress-Archive -Path experiments/results -DestinationPath "experiments-archive-$timestamp.zip"
```

#### Bash / Linux / macOS
```bash
tar -czf "experiments-archive-$(date +%Y%m%d-%H%M%S).tar.gz" experiments/results/
```
